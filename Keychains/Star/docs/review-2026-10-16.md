# Gaze and charging review — October 16, 2026

## Scope and changes

The supplied message described a 40-degree patch, but this checkout still had
`HORIZONTAL_GAZE_FULL_DEG = 30`, no `gaze_expect.h`, and no matching diff file.
The review therefore covered the actual working copy, including the existing
manual-center implementation. The user confirmed updating it to 40 degrees.

Horizontal full travel is now 40 degrees; the neutral zone remains 4 degrees.
Nine test files use updated expectations or saturation fixtures, including the
earlier wake-origin and manual-center tests, which also needed changes to work
with 40 degrees. The new `gaze_expect.h` computes partial travel from the config.
Physical direction remains independently asserted. Tests also check both sides
of the neutral zone, partial travel at 30/35 degrees, full travel at 40/45 degrees,
and immediate movement after a manual zero. Existing vertical, sleep, touch and
gesture behavior checks remain in place.

## Unresolved charging detection

The reported failure when already plugged in at startup or wake matches the
current voltage-only detector. `BatterySupply::sample()` initializes its baseline
from the first measurement, then requires a confirmed rise to infer charging.
A saved unconfirmed state and steady VBAT supply no such evidence.

A desktop reproduction using the actual detector produced:

| Model input | Charging inferred |
| --- | --- |
| Cold boot at steady 4.149 V, observed for 60 seconds | False |
| Restore that unconfirmed snapshot and observe the same voltage | False |
| Restore a previously confirmed charging state at the same voltage | True |
| Unconfirmed state, then 4.134 → 4.176 V reconnect step | True |

The [Rev3 schematic](https://files.waveshare.com/wiki/ESP32-S3-Touch-LCD-1.28/ESP32-S3-Touch-LCD-1.28-Sch.pdf)
shows GPIO1 sensing VBAT through a divider; neither charger STAT nor VBUS is
wired to an ESP32 input. A steady voltage alone cannot distinguish an attached
cable from a disconnected battery at the same voltage. Reliable standalone
connection detection needs an additional hardware signal. USB presence would
still be different from measuring charge current or detecting completion.

A brief COM10 serial capture during this review produced a power-on boot log
reporting VBAT 4.143 V, estimate 95%, and `charging-inferred=1`, followed by the
normal start-asleep sequence. This demonstrates one retained charging startup;
it does not resolve the unconfirmed-startup case or measure charging current.
No host confirmation command was sent, no charging thresholds were changed,
and no firmware was uploaded. The earlier physical test and limitations remain
documented in [the charging report](charging-test-2026-10-15.md).

## Validation

All 16 desktop test programs passed using the installed portable Zig 0.15.2 C++
compiler: shake, left/right wake, motion, periodic gaze, wake origin, horizontal
tracking, orientation loop, touch, touch IRQ, manual center, always-on, battery,
animation, motion/sleep, gaze/layout, and soak. Changed tests were rerun after
their final corrections. The normal soak and an additional build with verified
undefined-behavior instrumentation each completed 354,235 frames over three
simulated hours with zero reported problems. The local Windows compiler lacks
the AddressSanitizer runtime, so this does not claim an AddressSanitizer pass.

The ESP32 firmware compiled successfully with Espressif Arduino core 3.3.11 and
`esp32:esp32:esp32s3:FlashSize=16M,PSRAM=enabled,CDCOnBoot=default`: 478,999 bytes
of program storage and 41,348 bytes of global RAM. `git diff --check` passed.
Review build outputs and logs are under the ignored `build/review` directory.
The 40-degree firmware has been built but has not been tested on the display.
